# TAPtoTEN · Google Play 출시와 업데이트 안내

작성·정책 확인: 2026-09-28. Google 정책은 바뀔 수 있으므로 실제 제출 때 Play Console의 필수 작업과 오류 안내를 다시 확인한다.

## 1. 지금 어디까지 왔나요?

현재 개발자 계정 가입 및 본인인증 서류 제출을 마치고 결과를 기다리는 중이다. **개발자 본인인증과 게임 출시 심사는 서로 다른 절차**다. 본인인증이 끝나도 스토어 정보, 테스트, 게임 심사는 남아 있다.

- AAB: 게임 코드·이미지·음악을 묶은 **스토어 제출용 상자**. ABB가 아니라 AAB다.
- 서명 키: 내가 만든 업데이트라는 것을 증명하는 **앱의 도장**.
- 스토어 등록정보: 이용자가 보는 **가게 간판과 상품 설명**.
- 테스트: 정식 판매대에 놓기 전에 해 보는 **시범 운영**.
- 프로덕션: 일반 이용자가 검색하고 설치할 수 있는 **정식 출시**.

AAB는 휴대전화에서 직접 눌러 설치하는 파일이 아니다. Play Console에 올리면 Google이 기기에 맞는 설치 파일을 만들어 준다. 테스트도 Play의 테스트 초대 링크로 설치하는 방식이 좋다. [앱 생성·설정 안내](https://support.google.com/googleplay/android-developer/answer/9859152?hl=ko)

## 3. 준비물

### 게임 파일과 보관물

- 서명된 `.aab` 파일.
- 업로드 키 파일 `android/upload-keystore.jks`와 설정 파일 `android/keystore.properties`의 안전한 백업. 설정 파일에는 비밀번호가 있으므로 **GitHub·메신저·공개 문서에 올리지 않는다.** 암호화된 저장장소/비밀번호 관리자를 사용한다.
- 실제 안드로이드폰. 화면 잘림, 음악, 캐릭터 영상, 이어하기, 업데이트 후 기록을 확인한다.

Play App Signing을 사용하면 Google이 실제 배포용 서명을 관리하고, 우리는 업로드 키로 AAB에 서명한다. 업로드 키를 분실한 경우에는 재설정 신청 절차가 있지만, 평소 백업하는 것이 안전하다. 다른 스토어에도 같은 서명으로 배포할 계획이라면 첫 Play App Signing 설정 전에 별도로 검토한다. [서명·업로드 키 설명](https://developer.android.com/studio/publish/app-signing)

### 이용자에게 보여 줄 자료

| 준비물 | 권장 준비 방식 |
| --- | --- |
| 게임 이름·짧은 소개·자세한 소개 | 실제 기능만 설명. 예: “숫자 블록을 조합해 목표 합계를 만드는 리듬감 있는 퍼즐 게임” |
| 문의 이메일 | 실제로 확인하고 답변할 수 있는 주소 |
| 앱 아이콘 | 512×512 PNG |
| 대표 배너 | 1024×500, JPG 또는 투명도 없는 PNG |
| 게임 스크린샷 | 현재 플레이 화면을 세로 1080×1920, 3장 이상 준비 권장 |
| 개인정보처리방침 | 로그인 없이 열리는 공개 웹페이지 + 앱 안에서 볼 수 있는 링크/본문 |

스토어 스크린샷은 최소 2장이 필요하다. 게임 추천 노출용 이미지 요건까지 고려하면 세로 9:16, 1080×1920 이상 3장이 적합하다. 연구용 **780×1688은 긴 변이 짧은 변의 두 배를 넘으므로 그대로 스토어에 올리지 않는다.** 연구 원본은 보존하고 스토어용을 별도로 촬영한다. 기존 그림을 늘이거나 현재 없는 화면을 만들지 않는다. [Google 이미지 규격](https://support.google.com/googleplay/android-developer/answer/9866151?hl=en-GB)

개인정보를 수집하지 않는 앱도 개인정보처리방침이 필요하다. 실제 개발자 이름/연락처, 기기 내 진도·점수 저장, 수집·전송·공유 여부, 데이터 삭제 방법 등 실제 동작과 맞게 작성한다. 현재 코드 검토에서 광고·로그인·분석 SDK는 발견되지 않았지만, 제출 전 배포 빌드와 모든 의존성의 데이터 동작을 다시 확인한 뒤 Data Safety에 답한다. 인터넷 권한이 있다는 이유만으로 수집한다고도, 없다는 이유만으로 수집하지 않는다고도 판단하지 않는다. [사용자 데이터 정책](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en)

### 소유자가 결정할 내용

- 개인 계정인지 조직 계정인지 확인.
- 무료/유료, 출시 국가, 실제 대상 연령 결정.
- 어린이도 대상으로 한다면 해당 연령을 사실대로 표시하고 Families 정책 확인. 심사를 피하려고 연령을 다르게 적으면 안 된다.
- 그림·캐릭터·영상·음악·폰트의 배포/상업적 사용 권한 확인. 직접 만들었거나 AI로 만들었더라도 사용 도구의 약관과 참고 소재의 권리를 확인한다.
- 국가/계정/수익화 방식에 따라 콘솔이 요구하는 개발자 연락처·판매자 관련 추가 항목 확인.

[심사 준비 항목](https://support.google.com/googleplay/android-developer/answer/9859455?hl=en), [대상 연령 안내](https://support.google.com/googleplay/android-developer/answer/9867159?hl=en-GB)

## 4. 실제 출시 순서

### ① 본인인증 마무리

Google의 답변과 Console 홈의 남은 작업을 확인한다. 신규 개인 계정이라면 실제 Android 기기 확인이 추가로 요구될 수 있다. Console의 기기 인증 안내에서 QR 코드를 열고 Play Console 모바일 앱으로 진행한다. 이 확인에는 루팅하지 않은 Android 10 이상 실물 기기가 필요하다. [기기 인증 안내](https://support.google.com/googleplay/android-developer/answer/14316361?hl=en)

### ② 게임 등록 공간 만들기

Play Console → **모든 앱 → 앱 만들기**. 이름·기본 언어 입력, 유형은 **게임**, 무료/유료 선택, 연락처 입력. Google의 약관·선언은 계정 소유자가 확인한다. 카테고리는 실제 게임에 맞춰 퍼즐 등을 선택한다. [앱 생성 안내](https://support.google.com/googleplay/android-developer/answer/9859152?hl=ko)

### ③ 스토어 정보와 정책 설문 채우기

대시보드의 필수 작업 목록을 따라 아이콘·배너·소개·스크린샷을 등록한다. 앱 콘텐츠에서 개인정보처리방침, 광고 여부, 앱 접근 권한, 대상 연령, 콘텐츠 등급 설문, 데이터 보안을 작성한다. 광고/로그인이 실제로 없다면 그에 맞게 답하되 템플릿 답변을 무조건 복사하지 않는다. 콘텐츠 등급은 임의로 “전체 이용가”를 고르는 것이 아니라 설문 결과를 확인한다. [심사 준비 안내](https://support.google.com/googleplay/android-developer/answer/9859455?hl=en)

### ④ 먼저 내부 테스트

**테스트 및 출시 → 테스트 → 내부 테스트 → 새 버전 만들기**에서 서명된 AAB를 올린다. 첫 출시의 Play App Signing 설정을 확인하고, 변경사항 설명을 입력하고, 테스트용 버전을 배포한다. 초대할 Google 계정을 등록한 뒤 참여 링크를 보낸다. 내부 테스트는 정식 공개가 아니며 필수 비공개 테스트와도 다르다.

여기서 꼭 해 볼 것:

- 로고 → 커버 → 메뉴가 정상 표시되는지.
- LIMITLESS 튜토리얼 10단계에서 종료 후 다시 실행하면 해당 단계에서 시작하는지.
- 세 모드, 정오답 산식, LIMITLESS 본게임의 오답 −1초가 정상인지.
- 캐릭터 영상이 소리만 나오지 않고 화면도 재생되는지.
- 앱을 백그라운드로 보낸 뒤 돌아왔을 때 음악/시간/화면이 정상인지.
- 비행기 모드에서도 설치된 게임을 실행할 수 있는지.
- 업데이트 테스트에서 점수·설정·진도가 유지되는지.

### ⑤ 필요한 경우 비공개 테스트

**2023-11-13 이후 만든 개인 개발자 계정**이라면 정식 출시 권한 신청 전 **최소 12명이 연속 14일 동안 참여 상태를 유지하는 비공개 테스트**가 필요하다. 단순히 이메일 목록에 추가하는 것만으로는 부족하며 참여 링크에서 참가하고 실제로 게임을 테스트해야 한다. 중간 이탈에 대비해 여유 있게 모집하고 의견·수정 내용을 기록한다.

조건을 채운 다음 대시보드에서 프로덕션 액세스를 신청한다. 14일이 지났다고 자동으로 승인되지는 않는다. 조직 계정 등 다른 계정 유형에는 이 신규 개인 계정용 조건을 일괄 적용하지 않고 콘솔의 실제 요구사항을 따른다. [현재 테스트 요건](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en-GB)

### ⑥ 정식 출시 심사와 공개

정식 출시 권한을 얻고 필수 항목을 완료하면 **프로덕션**에 검증한 버전을 올리거나 테스트 버전을 승격한다. 국가와 출시 내용을 확인하고 심사에 제출한다. 오류·정책 안내가 나오면 수정한다. 심사 승인과 게시 설정에 따라 스토어에 공개되며 심사 기간을 미리 확정할 수는 없다. 본인인증 완료일과 게임 공개일은 같지 않을 수 있다.

## 5. 앞으로 수정은 어떻게 하나요?

지금처럼 “여기 바꿔줘”라고 요청하면 된다. 단, **웹 업데이트와 앱 업데이트는 배달 방법이 다르다.**

| 변경 대상 | 반영 방법 |
| --- | --- |
| Vercel 웹 게임 | 수정·검증 → Git push → 연결된 웹 배포 |
| 설치된 Android 게임 | 수정·검증 → 버전 번호 증가 → 새 AAB 제작 → 같은 Play 앱에 새 버전 등록 → 테스트·심사·배포 |
| 스토어의 설명/소개 이미지 | Console의 등록정보 수정. 게임 코드가 그대로면 보통 새 AAB는 필요 없지만 변경사항 심사가 있을 수 있음 |

이 프로젝트는 웹주소를 열기만 하는 앱이 아니라 **게임 파일을 앱 안에 넣는 구조**다. 따라서 Git push나 Vercel 배포만 해서는 이미 설치된 앱이 바뀌지 않는다.

예를 들어 첫 파일이 표시 버전 `1.0`, 내부 번호 `1`이라면 다음 파일은 `1.0.1`, 내부 번호 `2`로 만든다. 내부 번호 `versionCode`는 새 업로드마다 올리고 이미 쓴 번호를 재사용하지 않는다. 테스트에서 사용한 동일 파일을 정식으로 승격하는 경우에는 새 파일을 만들 필요가 없다. [업데이트 준비 안내](https://support.google.com/googleplay/android-developer/answer/9859350?hl=ko)

향후 작업 요청 예시:

> “이 부분 수정하고 연구기록 남겨줘. 기존 진도와 최고기록이 유지되는지 확인하고, Play 업데이트용 AAB도 만들어줘. Git도 푸시해줘.”

출시 여부는 소유자가 최종 결정하며 코드 수정/AAB 제작이 자동으로 정식 공개되는 것은 아니다.

### 업데이트 때 기록을 지키려면

앱 ID, Play의 서명 체계, 저장 키·저장 위치를 유지한다. 저장 형식을 바꾸면 기존 기록을 새 형식으로 옮기는 코드도 함께 만든다. 같은 앱을 **삭제하지 않고 업데이트**하는 것이 핵심이다.

이 게임의 현재 보존 범위는 LIMITLESS 튜토리얼 단계, 세 모드 최고기록, 설정이다. ENDLESS/TIMELESS의 진행 중인 판을 재개하는 기능은 아니다. 일일 기록은 날짜가 바뀌면 초기화된다. 앱 삭제·데이터 삭제·기기 교체 복원이나 웹 기록을 새 Android 앱으로 자동 이전하는 기능은 제공하지 않는다.

첫 공개 전, 그리고 저장 방식 변경 때는 Play 내부 테스트에서 **이전 버전 설치 → 기록 생성 → 새 버전으로 업데이트 → 기록 비교**를 수행한다. 자동 테스트를 통과해도 이 실물 기기 검증을 대체하지 못한다.

## 6. 개발용 AAB 제작 메모

필요 도구: Node.js 22, Java 21, Android SDK Platform 36 및 해당 Gradle 빌드 도구. SDK는 Google 약관에 동의한 뒤 설치한다. 프로젝트 로컬 도구를 사용할 경우 `.android-tools/jdk/Contents/Home` 및 `.android-tools/sdk`를 빌드 스크립트가 사용한다. 시스템의 JAVA_HOME/ANDROID_HOME이 이미 설정되어 있으면 그 설정을 우선한다.

```bash
npm ci
npm test
npm run android:bundle
```

출력: `android/app/build/outputs/bundle/release/app-release.aab`.

이 Mac의 첫 검증본은 별도로 `releases/TAPtoTEN-1.0-code1.aab`에 보관한다. 제작 도구는 프로젝트의 `.android-tools/`에 설치했고 전역 Java/SDK 설정은 변경하지 않았다. 선택적 도구 사용 통계 전송에는 동의하지 않았다.

이 Mac에는 검증용 bundletool 1.18.3도 있다. 다음 빌드의 버전 번호를 올린 뒤 아래처럼 검증·배포용 복사본·기록을 만들 수 있다. 기존 파일/기록은 덮어쓰지 않으므로 새 기록 경로를 지정한다.

```bash
node scripts/verify-aab.mjs docs/releases/YYYY-MM-DD-version
```

### 이번에 생성한 키 백업

아래 두 파일은 **이 Mac에만 있으며 외부 백업은 아직 하지 않았다.** 둘 다 소유자만 읽고 쓸 수 있게 설정했고 Git에서 제외했다.

- `android/upload-keystore.jks`: 실제 업로드 키. 별칭은 `upload`.
- `android/keystore.properties`: 키 위치·별칭·자동 생성한 강한 비밀번호. 내용을 채팅이나 Git에 붙여 넣지 않는다.

두 파일을 비밀번호 관리자의 보안 첨부 또는 암호화된 외장 저장장치에 함께 보관한다. 폴더를 일반 공유 링크로 공개하거나 `.jks`만 복사하고 비밀번호를 빼먹지 않는다. 다음 업데이트에서는 **이 키를 재사용**한다. 아직 Play에 등록한 키는 아니며, 첫 업로드 때 해당 앱의 업로드 인증서로 연결된다.

`android/keystore.properties`가 없으면 명령이 멈춘다. 서명하지 않은 AAB를 제출용으로 착각하지 않기 위한 점검이다. 실제 키와 설정 파일은 Git에 포함하지 않는다. Gradle 결과·로컬 도구·`releases/`도 Git에 넣지 않는다.

키를 처음 직접 만들 때는 Java 21의 `keytool`을 사용하고 비밀번호를 비공개로 입력한다. 기존 키가 있다면 새 키를 만들지 말고 기존 것을 사용한다.

```bash
keytool -genkeypair -keystore android/upload-keystore.jks \
  -storetype PKCS12 -keyalg RSA -keysize 3072 \
  -validity 10000 -alias upload
```

설정 파일의 필요한 필드는 `storeFile=upload-keystore.jks`, `storePassword`, `keyAlias=upload`, `keyPassword`다. 키 파일과 비밀번호 파일은 소유자만 읽을 수 있게 보관한다. CI를 사용할 때는 GitHub의 일반 파일이 아니라 Actions Secrets를 사용한다. 기존 `.github/workflows/release-aab.yml`은 키 관련 시크릿 4개가 있어야 실행된다. 시크릿 등록/원격 빌드는 별도 작업이다.
